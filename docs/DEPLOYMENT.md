## 3. Подготовка серверного окружения

Сначала проведите развёртывание в отдельном Firebase-проекте и Workers с другими именами, отдельными очередями и секретами. Для стенда нужно согласованно заменить имена/идентификаторы во всех настройках. Следующие имена относятся к подготовленной конфигурации рабочего проекта, поэтому не выполняйте их как команды создания стенда без замены.

```sh
pnpm exec wrangler queues create test-lms-jobs
pnpm exec wrangler queues create test-lms-jobs-failed
```

R2 не подключается. Копии очисток шифруются AES-256-GCM и сохраняются в закрытой коллекции Firestore. Автоматического удаления нет. Основная очередь и очередь неуспешных доставок подключаются через bindings. Подробности бесплатной схемы, лимиты и хранение ключей: [FREE_PLAN.md](FREE_PLAN.md).

Создайте отдельную сервисную учётную запись Google Cloud для серверной работы с Firestore нужного проекта. Ей требуется доступ к данным, но не управление проектом. Её JSON с `project_id`, `client_email`, `private_key` задаётся целиком в `FIREBASE_SERVICE_ACCOUNT`; файл не помещается в публикуемую папку или Git.

| Worker | Секреты |
| --- | --- |
| API | `GEMINI_API_KEY`, `FIREBASE_SERVICE_ACCOUNT`, `INTERNAL_DISCORD_TOKEN`, `BACKUP_ENCRYPTION_KEY` |
| Discord | `DISCORD_WEBHOOK_URL`, `INTERNAL_DISCORD_TOKEN` |

Внутренний токен — отдельное случайное значение, одинаковое у двух Workers. Не используйте для него ключ Gemini или URL вебхука. Старые секреты Gemini/Discord можно сохранить, если они настроены в соответствующих Workers; их значения нельзя проверять выводом в консоль.

Секреты добавляются в Cloudflare → Worker → Settings → Variables and Secrets с типом Secret или через `wrangler secret put NAME --config CONFIG`. Учтите, что `secret put` сам публикует новую версию Worker; для согласованного выпуска можно использовать версии или загрузку секретов вместе с кодом. См. [Cloudflare Secrets](https://developers.cloudflare.com/workers/configuration/secrets/). В TOML секретных значений быть не должно.

## 4. Согласованный переход

1. Подготовьте проверенную копию базы и сохраните предыдущие версии клиента, Workers, правил и индексов. Копии операций очистки не заменяют резервную копию базы перед миграцией.
2. Пройдите сценарии следующего раздела на стенде. Уточните число учеников, объём недельных событий и допустимую нагрузку; не обещайте поддержку 500 одновременно работающих учеников на основании одного ограничения чтения профилей.
3. Выберите время без занятий, закройте ученикам вход на время переключения и завершите старые открытые сессии. Правила не могут запретить уже загруженному старому клиенту рисовать интерфейс, поэтому после перехода требуется перезагрузка.
4. Создайте ресурсы, задайте серверные секреты и подготовьте индексы. При публикации индексов сохраните существующие индексы проекта, отсутствующие в локальном файле; не подтверждайте их удаление. Дождитесь готовности новых индексов.
5. Опубликуйте сначала Discord Worker, затем API Worker. Discord перестаёт иметь публичный relay; API получает `DISCORD_SERVICE`, `JOBS`, `LMS_RUNTIME`. Миграция new_sqlite_classes создаёт класс, доступный на Free. До новых правил нельзя создавать архивы и другие серверные данные: старые правила ещё не закрывают доступ к ним.
6. Под учётной записью владельца выполните добавочную миграцию назначений `POST /migration/project-assignments`. Она создаёт отсутствующие `users/{uid}/assignments/{id}`, не удаляет и не меняет исходные задания. Повтор безопасен. Для неё нужны авторизованный клиент нового API и закрытый на время перехода сайт.
7. Опубликуйте новые правила и совместимый клиент с `enabled: true`, корректным `apiBase` и свежим идентификатором ресурсов. Публикуйте все изменённые JS вместе, включая `lms_event_outbox.js`, `lms_api.js`, `lms_control_ui.js`; Excel/Word также обновляются с новой версией URL.
8. Проверьте владельца и отдельного ученика; только затем откройте сайт для занятий.

Команды публикации, применяемые в этом порядке в согласованном окне:

```sh
pnpm exec firebase deploy --only firestore:indexes --project my-lms-project-13739
pnpm exec wrangler deploy --config wrangler.discord.toml
pnpm exec wrangler deploy --config wrangler.api.toml
# Здесь: добавочная миграция назначений под UID владельца.
pnpm exec firebase deploy --only firestore:rules --project my-lms-project-13739
# Здесь: публикация совместимого клиента через действующий хостинг сайта.
```

Для миграции в закрытом новом клиенте под владельцем можно использовать `await LmsApi.request('/migration/project-assignments', {})`. Это добавочная служебная операция выпуска, а не ученическая команда. Не сохраняйте и не пересылайте Firebase ID token.

Конфигурации в репозитории целятся в существующие Workers. Их прежние необязательные доменные routes следует проверить в панели: закрытый Discord Worker не должен оставаться доступным через старый custom route. GitHub push не заменяет публикацию Workers/Firestore; способ публикации страницы зависит от фактического хостинга.

## 5. Проверка на стенде и после перехода

- Владелец видит собственный административный чат; другой пользователь не получает права при изменении `role` в клиенте.
- Ученик открывает свои тесты, печать, сочетания, Word, Excel, код, карточки и игры; запрет конкретного модуля сохраняется. В новых профилях доступ к Word/шахматам/заданиям включается владельцем по необходимости.
- Word сохраняет черновик и результат, Excel проверяет верную/неверную формулу. Одна попытка не увеличивает счётчики при повторе запроса или зачёте в задании.
- Старые задания после миграции видны адресатам. Чужие задания, профили и переписки из ученического аккаунта недоступны.
- Создание задания даёт карточку; до нажатия оно не выдано. Ученик не может вызвать маршрут создания, подтверждения или очистки.
- Очистка тестовых записей даёт список и число, проверяет копию, удаляет только после кнопки. Повтор кнопки безопасен, восстановление требует новой кнопки и не затирает новые результаты.
- Ежедневный и недельный отчёты сохраняются в LMS. Отказ/429 Discord виден в задачах, повтор не теряет подтверждённые части. Отправляйте реальные пробные сообщения только в согласованный тестовый канал.
- При временной потере сети и перезагрузке очередь событий возобновляется в том же аккаунте. В другом аккаунте чужая очередь не отправляется.
- Открытие модулей, выполнение заданий и выход не создают необработанных ошибок в консоли; измерьте время ответа и количество запросов при ожидаемом числе учеников.

## 6. Начало работы через чат

При первом выпуске `scripts/initialize-control.mjs` включает уже запрошенные владельцем отчёты и начинает ручной 14-дневный пилот. Повторный запуск сохраняет существующие настройки. Отдельно владелец подтверждает:

1. Состав групп, если нужно сравнение с группой.
2. «Критерии профи» — предложенные пороги и обязательные направления можно изменить перед подтверждением. До этого оценка «профи» не применяется.

Через 14 суток автоматическая выдача по-прежнему выключена. Она включается только отдельной командой «Включи автоматическую выдачу заданий» и кнопкой владельца. Отключение также доступно через чат. Очистки автоматически не включаются никогда.

## 7. Если требуется откат

При проблеме после переключения закройте доступ к занятиям, выключите автоматические назначения и плановые отчёты через владельца, устраните причину или восстановите совместимый набор клиента/Workers/правил. Не возвращайте только `enabled: false`: старый клиент не может записывать результаты по новым правилам. Не возвращайте прежний общий доступ Firestore без отдельного решения владельца — он снова откроет чужие данные.

Дополнительные коллекции и резервные копии сохраняются. Откат кода не должен удалять результаты после выпуска. Очистка новых данных возможна лишь через предусмотренное подтверждение. Неудачные фоновые задачи доступны командой «Ошибки отправки», копии очисток — командой «Копии».
